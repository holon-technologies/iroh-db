- One strict `/iroh-db/sync/1` control ALPN with nonce-bound mutual domain proof, canonical 1 MiB frames, 4,096-reference pages, and a 65,536-reference session budget.
- Read-only iroh-blobs providers and authorized pull-based immutable transfer; control frames never carry commit bytes.
- Signature, domain, epoch, trust, dependency, AEAD, schema, target, and CRDT validation before atomic remote persistence.

- Real two-way and three-peer reconciliation after offline concurrent writes, arbitrary pairwise ordering, duplicates, and clean process restart.
- iroh-gossip on an epoch-derived unguessable topic with bounded signed hash/frontier hints, replay counters, and ordinary sync as the only apply path.
- Signed encrypted snapshot bootstrap through iroh-blobs, durable commit coverage and author-sequence baselines, followed by tail-only reconciliation.
- Updated public networking/bootstrap documentation and explicit M2 threat boundaries.

## Threat-Model Delta

- QUIC authenticates devices; M2 authorization additionally requires persisted domain membership. Possessing the symmetric domain key alone does not grant write acceptance.
- Blob providers are deliberately read-only. Peers pull exact agreed hashes, preventing the disabled upstream push path from becoming an unauthenticated disk-write surface.
- Commit ciphertext, snapshot manifests, snapshot chunks, and application blobs remain encrypted at rest and in content-addressed storage. Hashes, endpoint identities, packet sizes/timing, and reconciliation frequency remain observable.
- Gossip is availability-only. Its topic is epoch-derived, messages are signed and bounded, replayed counters are ignored, and a hint never authorizes or directly applies state.
- Snapshot references and `DomainSeed` are sensitive bootstrap material and require an authenticated out-of-band handoff until M3 invitations exist.
- Resource exhaustion is bounded per frame/session and per reconciliation graph. A malicious authorized peer can still consume bounded bandwidth/CPU or withhold data; explicit retries and snapshots repair availability, not Byzantine liveness.
- Revocation and key rotation are intentionally not claimed by M2. Those controls are the M3 gate.

## Scope Boundary

M2 trust administration is owner-configured and device-oriented. It does not yet provide signed invitations, delegated capabilities, revocation control chains, epoch rotation, multiple active domains in one database, group roles, or user/device grouping. Multi-source blob fan-in and adaptive scheduling remain M4 work. Production audit, fuzz, repair, backup, observability, and long-running chaos gates remain M5 work.
