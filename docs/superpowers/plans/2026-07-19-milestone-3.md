# Milestone 3: Sharing and Domain Control Implementation Plan

## Goal and Success

Replace M2's manually copied seed/trust bootstrap with durable signed domain authority. One store can host several independently encrypted domains under one stable device identity. Invitations grant least-privilege capabilities to a named endpoint; revocation advances the epoch at a signed causal cut; a removed endpoint cannot authenticate, author, fetch, gossip, or decrypt new-epoch data. Sharing is an explicit projection into an independent destination history.

## Resolved Model

- A database directory owns one device endpoint signer and an encrypted domain-key catalog. `IrohDb` is a cheap handle bound to one catalog domain; handles share the blob/store actors but never keys, queries, transactions, frontiers, subscriptions, or adapters across domain IDs.
- Each domain has a signed immutable genesis descriptor with fixed `MultiWriter`, `SingleWriter`, or `AppendOnly` consistency mode and an owner capability.
- Capabilities are strict canonical certificates naming one endpoint and explicit `READ`, `WRITE`, `INVITE`, `REVOKE`, `FETCH_BLOBS`, `SNAPSHOT`, and `ADMIN` bits. Delegation only narrows permissions, epoch scope, and depth; depth is capped at eight.
- The security control chain is single-successor by sequence. A control transition is signed by an active `ADMIN`/`REVOKE` capability and binds its predecessor, new epoch, cut frontier, revoked subjects, newly issued capabilities, and key-distribution digest.
- Rotation retains old keys locally for historical reads while changing all future commit/blob/snapshot/gossip derivation to the new key. Invitation payloads carry only the epochs the certificate permits.
- Online and offline invitation envelopes use the same signed payload. Offline tickets add XChaCha20-Poly1305 under a random one-time bearer secret and still reject import unless the local endpoint is the named subject.
- User/group metadata groups device endpoints for application UX only. Protocol authorization remains endpoint-specific.
- Projection reads typed source records and writes selected typed records into a destination-domain transaction. It never copies source commits, capabilities, transaction IDs, dependencies, or hidden history.

## Tasks

### Task 1: Multi-domain Key Catalog

Separate device credentials from domain epoch keys, add an owner-only encrypted catalog, and bind `IrohDb` handles to a `DomainContext`. Add create, attach, open, list, and close behavior while preserving the default-domain API. Prove independent frontiers, keys, records, blobs, and state roots in one directory.

### Task 2: Canonical Authority Objects

Add strict golden-coded `DomainDescriptor`, `PermissionSet`, `Capability`, `ControlCommit`, `Invitation`, and group metadata types. Use distinct signature contexts and hard bounds. Add tamper, unknown-bit, escalation, wrong-subject, wrong-domain, wrong-epoch, depth, and non-canonical tests.

### Task 3: Persisted Capability and Control State

Add domain descriptor, control head, capability, revocation, and group tables. Bootstrap the owner capability at domain creation. Make local and remote commit validation resolve `header.capability_id` against the control state before decryption/materialization and enforce consistency mode.

### Task 4: Invitation Workflows

Add targeted invitation issuance/export/import, one-time ticket encryption, replay-safe import, and an authenticated sync-ALPN invitation exchange. Import persists descriptor/capability/key material atomically before exposing the domain handle. No invitation material enters gossip.

### Task 5: Rotation, Revocation, and Rebase

Create signed control transitions that atomically advance the epoch, record the old-epoch cut frontier, rotate the symmetric key/topic, revoke selected endpoint capabilities/trust, and package new key grants for remaining members. Reject post-cut old-epoch forks as `RebaseRequired`; expose their IDs for explicit application projection.

### Task 6: Consistency Modes and Device Groups

Enforce multi-writer, single-writer transfer, and append-only schema/operation rules. Persist bounded user/group labels mapped to endpoint IDs without treating labels as protocol identity.

### Task 7: Projection Sharing

Add a typed projection API that copies explicitly selected current records into one destination-domain transaction. Test fixture scans prove source commit IDs, encrypted bodies, record IDs excluded by the predicate, capabilities, keys, and prior source history do not occur in destination commits.

### Task 8: Milestone Gate

Run the full quality gate plus invitation/capability attack matrices, two-epoch partition schedules, revoked-peer network attempts, multiple-domain isolation, projection privacy fixtures, and restart recovery. Record evidence in `docs/milestones/M3.md`; any privilege escalation, post-cut acceptance/decryption, cross-domain leakage, or silent data loss keeps M3 open.

## Gate

Milestone 3 passes only when an invited least-privilege member can synchronize exactly its allowed domain, delegated permissions cannot expand, a revoked endpoint cannot authenticate or decrypt new data after the causal cut, remaining devices converge at the new epoch, rejected offline writes are surfaced as rebase-required, multiple domains remain byte-isolated, and sharing reveals only the explicit projection.
